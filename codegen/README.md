# codegen

Derives `src/model/` from the GraphQL schema and the query.

```bash
npm install
npm run fetch-schema   # refresh schema.graphql from findopera.com
npm run generate       # rewrite src/model/generated.rs
```

The output is checked in on purpose. When the API changes, the diff is the
report: a field losing `@semanticNonNull` upstream shows up as `String`
becoming `Option<String>` and `FieldDoc::non_null` becoming `FieldDoc::new`,
which is exactly the change that makes every bare `{{that.field}}` in a
template start failing to parse. That is worth reading before you accept it.

## Why JavaScript

`validate()` from graphql-js is the reference implementation, so the query is
checked against the schema properly — unknown fields, bad arguments, wrong
variable types — before a line of Rust is written:

```
query does not validate against the schema:
  Cannot query field "subtitle" on type "Opera". Did you mean "title"?
```

The schema is itself generated by Grats from TypeScript, so the toolchain was
already here.

## Where nullability comes from

FindOpera's schema declares nothing with `!`: in the strict GraphQL sense
every field is nullable, because a null anywhere can signal an error. What it
carries instead is `@semanticNonNull`, which marks a position as only ever
null when the response has a matching entry in its `errors` array. That is the
property a template needs — "there is a value for every record" rather than
"this key is never JSON null" — and it is what `FieldDoc::non_null` means.

A template path is non-null only when every link above it is annotated:
`opera.language.name` is nullable even though `Language.name` is annotated,
because a recording's opera may have no language at all.

## Files

| | |
|---|---|
| `../schema/schema.graphql` | vendored from findopera.com |
| `../schema/recording.graphql` | the query, sent verbatim at runtime |
| `../schema/fields.mjs` | what the query cannot express |
| `../src/model/generated.rs` | the output |

`fields.mjs` covers three gaps. **Renames** hoist a subtree to a shorter path,
because GraphQL aliases rename within a level but cannot lift `opera.composer`
up to `composer`. **Derived fields** project single values out of a list —
a query can select `notedSingers`, but it has no way to say "the second one",
and the template language has no list syntax. **Descriptions** exist because
the schema documents almost none of the fields a template would use.

Every entry is checked against the query: renaming or projecting from
something the query does not select is an error, so this file cannot drift
either.
